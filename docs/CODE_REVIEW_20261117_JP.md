# N3MemoryCore MCP Lite コードレビュー（2026-11-17）

## 対象と方法

- 対象: `N3MemoryCore_MCP_Spec_JP.md` と `n3mc_mcp/` の現行実装。コードは変更していない。
- 優先度: **P1** は他用途のデータ損失につながり得る問題、**P2** は保存・再取得の契約または実用上の検索結果を損なう問題。
- 確認: ソースの経路追跡、Redis を使わない短い再現、`tests/test_processor.py` のモデル読み込みテスト以外（56 件成功、3 件除外）。Redis の本番データを保護するため、専用の `N3MC_REDIS_TEST_URL` がない状態で Redis 統合テストは実行していない。全テスト実行は途中で進まなくなったため中断した（停止箇所は未特定）。実機 Redis 上の再現や MCP クライアントからの往復確認は未実施。

## 指摘事項

### 1. [P1] 別の論理 DB のデータがあっても Redis 全体の永続化を無効にする

**箇所:** `n3mc_mcp/database.py:419-452`、指示書 §3.4（336-343 行）。

`_only_n3mc_keys()` は接続先の論理 DB だけを `SCAN` する。その DB が空なら `enforce_ephemeral()` が `CONFIG SET appendonly no` と `CONFIG SET save ""` を送る。しかし `CONFIG SET` は Redis サーバーの設定変更であり、`SCAN` は現在選択中の DB のキーしか見ない。たとえば N3MC が DB 0 を使い、別アプリの永続データが DB 1 にある場合、DB 0 が空なら永続化が無効になる。Redis 再起動時に別アプリのデータを失う恐れがある。

この危険は**指示書の判定手順そのもの**にも含まれる。選択 DB が空であるという条件だけで、サーバー全体の永続化設定を変更しない設計が必要。少なくとも専用 Redis インスタンスであることを明示的に確認できない場合は、設定変更を行わず通知に留めることを推奨する。

根拠: [Redis SCAN（選択中 DB のみ）](https://redis.io/docs/latest/commands/scan/)、[Redis CONFIG SET（サーバー設定の変更）](https://redis.io/docs/latest/commands/config-set/)、[Redis SAVE（インスタンスの全データを保存）](https://redis.io/docs/latest/commands/save/)。

### 2. [P2] 保存時に前後の空白・改行が失われる

**箇所:** `n3mc_mcp/database.py:648-683`、指示書 §3.13（773-811 行）、§3.11（645-660 行）。

`save_memory()` は `sanitize_surrogates(content).strip()` をそのまま保存経路へ渡す。再現では入力 `repr(' \nAAA\n ')` が `_save_single()` に `repr('AAA')` として渡った。長文も同じ入口を通るため親ドキュメントの `content` から前後の空白・改行が落ちる。指示書は、可視文字を含む本文はサロゲート除去以外を行わず原文どおり保存するとしている。先頭インデントや末尾改行を含むログ・コード・資料の一字一句の復元ができない。

空白だけの入力の拒否判定には `strip()` を利用できるが、保存する値にはサニタイズ後の元本文を渡す必要がある。前後空白を含む短文・親ドキュメント双方の保存と再取得を検証することを推奨する。

### 3. [P2・仕様の矛盾] 検索結果のコードブロックが `[code omitted]` に置換される

**箇所:** `n3mc_mcp/processor.py:72,490-492`、`n3mc_mcp/server.py:122-132,475-483,522-531`、指示書 §3.11（650-660 行）、§10-3（1354 行）。

親ドキュメントの Redis 上の本文はコードブロックを保持するが、`search_memory` の `_hit()` は出力時に `purify()` を呼び、三連バッククォートで囲まれた部分を削除する。`list_memories` と `recall_thread` の表示も同じ。再現では `heading\n```python\nprint(1)\n```\ntail` が `heading\n[code omitted]\ntail` と表示された。ユーザーは MCP ツールの表示から原文を取得できない。

指示書 §3.11 と §4.3 は全文を verbatim で**返す**としている一方、§10-3 はコードブロック置換を許している。まず公開契約を一本化する必要がある。後からコードを含む文書を原文復元する用途を維持するなら、検索・スレッド取得で全文を表示できる経路と、その往復テストが必要。

### 4. [P2・設計上の制約] 重複ガードが owner/session にまたがって共有される

**箇所:** `n3mc_mcp/database.py:92-100,722-736,808-849,1693-1803`、指示書 §3.8（550-570 行）と §6（1063 行付近）。

ガードキーは本文の SHA-1 だけで `mem:sha:<sha1>` / `docsha:<sha1>` として作られ、`owner_id` と `session_id` を含まない。結果として、同じ Redis を共有する別オーナー B が A と同じ本文を保存すると、B の行が存在しなくても `duplicate` になる。同一オーナーでも別セッション B に同じ本文を保存できない。後でセッション A を一括削除すると、B に紐づく記録は残らない。指示書が案内する複数アカウントの分離・セッション単位の管理と噛み合わない。

これは現行コードだけでなく、指示書のガードキー設計に由来する。重複をオーナー単位またはセッション単位のどちらで定義するかを決め、キーの名前空間と旧ガードの移行・削除規則を合わせて検討することを推奨する。

### 5. [P2・設計上の制約] 検索候補のオーナー判定が上位 100 件の取得後

**箇所:** `n3mc_mcp/database.py:1334-1391,1393-1472`、指示書 §3.12（681-711 行）。

KNN と BM25 はともにオーナー条件なしで最大 `min(limit * 5, 100)` 件を取得し、その後 Python 側で `owner_id` を除外する。別オーナーの高順位レコードが候補枠を埋めると、自分の関連レコードが 101 位以降にあり、存在しても検索結果が空になる。BM25 に一致しない言い換え検索では、ベクトル側の候補漏れを補えない。複数アカウントで Redis を共有する運用ほど起こりやすい。

これも指示書の Python 側フィルタリングに沿った実装であり、仕様レベルの制約。RediSearch で安全なオーナーフィルタをクエリ前に適用する方法、または別インデックス等の分離を検討することを推奨する。実機での発生頻度は未測定。

## 確認範囲の限界

Redis Stack の専用テストインスタンスと MCP クライアントを使った end-to-end 評価は行っていない。したがって検索スコア、TTL、競合状態、Windows/他 OS での起動を合格と判定した文書ではない。指摘 1・4・5 はソースと仕様から導いた経路上の問題で、実機 Redis による再現は未実施。指摘 2・3 は Redis を使わない再現で入力・表示の変化を確認した。
